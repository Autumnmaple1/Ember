# 情境保存与异常回复修复

日期：2026-11-07。

## 情境保存

面对面模式原来要求两个位置字符串完全相同。用户把同一处地点分别写成简称和全称时，会被前端校验阻止；失败提示又不靠近保存按钮，看起来像点击没有反应。

现在面对面只填写一个“共同位置”，提交时明确将双方位置保存为同一值。远程和未知模式仍分别填写，后端不会通过模糊匹配擅自判断两人同处一地。

保存中、成功、失败及后台忙碌原因显示在按钮旁；失败保留输入，可以重试。后台回复或状态更新期间仍可编辑，任务结束后再保存。并发场景变化继续返回冲突，供用户核对后重新提交。

## 最近回复的原因与修正

只读检查真实服务最近的对话、状态和工作记忆，发现几个相互加强的问题：应用名被当作陌生人的名字；主动消息曾以一两分钟的间隔连续补充自我分析；旧内心和轨迹重复解读同一句表达反馈，使后续回复偏向受伤、自辩和自我解释。还出现了没有来源的查课表说法，以及把晚上直接称为深夜。

本次没有删除或改写真实聊天、情绪、人设及旧状态。修复的是生成时使用它们的方法：

- 普通回复保留 PAD、场景、目标和来源，不再将推演的内心独白及综合轨迹直接作为台词脚本。观察面板和内部状态演化仍保留这些字段。
- 空闲演化区分本次新增对白和旧背景；没有新输入时，不逐轮加重对旧反馈的负面解读。
- 主动发言默认至少间隔 600 个现实秒，尝试前持久记录计时，重启与游戏读档不重置它。用户未回应一次主动补充时，不继续补发；旧消息通过兼容规则识别。正常用户对话不受此限制。
- 后端提供当前及明天的日期、星期；没有实际资料或工具结果时，不声称已查阅课表等材料。
- 结合上下文识别 Ember 对当前角色的称呼。收到表达方式反馈时，优先简短接住并重新表达，减少防御式追问和长篇自我分析。

`PROACTIVE_MIN_INTERVAL` 在本机 `.env` 或容器 `deploy/service.env` 配置，默认 600，单位为现实秒。它是最小间隔，不保证到时一定主动发话；主动开关、勿扰、睡眠、额度和内容判断仍生效。计时文件为运行目录下 `data/state/proactive.json`，异常时保留文件并暂停主动发言，避免失控补发。

## 验证方式

自动测试使用临时角色配置、随机测试数据库和模拟模型。覆盖面对面共同位置、保存失败重试、忙碌提示、并发冲突、手机视图，以及主动计时持久化、旧记录兼容、连续唤醒、损坏计时记录和回复上下文。

本轮结果：独立 55433 PostgreSQL 实例上的后端完整回归 **316 项通过**；前端单元 **32 项通过**，lint、构建与五组浏览器回归全部通过。后端仍有现有 FastAPI 生命周期接口弃用警告，前端构建仍提示 Live2D 分包较大，没有测试失败。

另用两轮合成对话请求真实模型，检查表达反馈和“Ember，明天有什么安排”；两次均成功，没有连接真实聊天数据库。抽查输出保存在 Git 忽略的 `output/reply-repair/`，不把私人聊天复制到项目文档。

这些规则用于减少已观察到的冲突，不能保证模型每次表达都自然。Android／Windows 双端与同步计划继续保留，本轮不扩展该计划。

## 更新与回退

本轮已实际完成本机容器更新：更新前两次确认无模型任务或存档任务正在运行，更新后应用健康，数据库、长期记忆和场景均就绪。通过接口分页比较原有 **35 条**消息的完整内容哈希，全部一致；手机尺寸真实页面已显示新的共同位置输入框。诊断没有保存真实场景，也没有发送聊天，临时验证登录均已注销。测试专用 PostgreSQL 已停止，业务数据库保持运行。

```powershell
$env:EMBER_SERVICE_IMAGE='ember-service:before-reply-fix-20261107'
docker compose --env-file deploy/service.env -f compose.service.yml up -d --no-deps --no-build --wait --wait-timeout 240 ember
Remove-Item Env:EMBER_SERVICE_IMAGE
```
