# Ember 前端交互与游戏体验改造计划

版本：2026-10-20。依据当前源码与仓库演示截图；本次没有启动生产后端、调用模型或修改运行数据。

执行更新（2026-11-02）：M2–M6 的工程交付、验证和恢复方式见 [最新交付记录](frontend-completion.md)。本文保留设计时的目标与分期；真人研究结果需按独立记录表执行，不将自动检查当作参与者结果。

## 1. 建议与产品定位

建议采用“重构前端体验与状态架构，延续现有 Python 角色引擎”的路线。先交付可靠的聊天、声音、历史和场景反馈，再增加有意义的游戏循环。

产品定位：**以对话为主要操作、以角色生活为持续背景的场景式陪伴游戏**。玩家应当随时知道“她在哪里、我们如何交流、我的操作有没有生效、接下来可以做什么”。

这是产品与交互重构，不只是视觉改版。默认优先桌面浏览器，同时做好手机端适配。游戏感主要来自可观察的生活、可参与的活动、可信的反馈和可回顾的共同经历；不依赖数值刷取或频繁要求玩家上线。

### 三条路线

| 路线 | 工作内容 | 收益与代价 | 建议 |
|---|---|---|---|
| A：改良现有界面 | 修复输入、滚动、声音、层级和反馈，拆出基础组件 | 最快缓解问题；复杂交互继续增长时仍需重构 | 作为第一阶段交付 |
| B：重做前端体验 | 新应用框架、视图切换、统一状态与播放控制、场景和回忆、存档工作流 | 能系统解决问题；需要协议补齐和一定素材制作 | **推荐主线** |
| C：完整生活模拟游戏 | 可探索地点、移动、日程、活动系统、物品与内容制作工具 | 可玩空间更大，也引入地图、规则、内容量及存档复杂度 | 在 B 的活动原型得到验证后启动 |

现阶段没有充分理由整体替换对话与记忆后端。React 承担可访问的界面，Pixi/Live2D 承担角色表现；如果以后需要可行走场景、碰撞、场景编辑，再做独立的二维引擎验证，依据实际性能和内容工作流决定是否迁移。

## 2. 当前问题审计

以下为源码可确认的行为或结构问题；视觉部分参考仓库截图，尚未进行当前版本的实际用户测试。

| 优先级 | 现状与证据 | 对体验的影响 | 改造方向 |
|---|---|---|---|
| P0 | 聊天区默认收起，主画面没有稳定的最新对白承载区 | 用户先看到背景和调试状态，回复可能被隐藏 | 最新回复始终可见，历史是另一个层级 |
| P0 | 每次消息更新都会调用滚到底部；初始化连续设置多个滚动定时器 | 翻阅历史时被拉回，滚动位置不可信 | 阅读锚点、新消息提示、接近底部时才跟随 |
| P0 | 输入框 Enter 不检查中文输入法组合状态 | 选字可能误发送 | 支持 composition；多行输入和明确快捷键 |
| P0 | 发送前先请求配置；忙碌时只弹红色提示 | 没有即时响应，也没有等待、打断或排队的明确选择 | 草稿独立保存，状态就地反馈，补齐真实取消 |
| P0 | 语音事件处理读取初次挂载的 autoPlay；另一条件 !isPlaying 又绕过关闭开关 | “语音关”可能仍播放，开关不可信 | 单一播放器、最新设置、严格的播放策略 |
| P0 | audio 事件只有音频内容，没有消息、轮次和播放请求标识；手动播放同样广播 | 重播、晚到音频和多个页面容易混淆 | 音频绑定轮次；手动重播只回到请求客户端 |
| P0 | window 级右键监听，按 Canvas 矩形及相对高度判断头/身体 | 透明区域也能触发；缺少触屏与键盘替代 | 模型命中区域、语义动作、明确按钮入口 |

| P1 | 状态面板固定 600px；角色固定 1200×1800 后用 CSS 缩放；主要布局没有窄屏规则 | 小屏拥挤，角色尺寸和位置不随场景布局适配 | 容器驱动布局与渲染尺寸，安全区和软键盘适配 |
| P1 | PAD、内部活动、目标及独白同时高曝光 | 玩家像在看运行面板，注意力难集中；角色过度透明 | 玩家层用可观察描述；深层状态进入可选观察模式 |
| P1 | 独白自动出现、数秒后自动消失，且悬浮框 pointer-events:none | 长内容来不及读，也不能主动停留 | 默认不打断，点击展开，可固定和回看 |
| P1 | 后端只有“思考”大状态，准备场景、生成、播音、等待混用 | 用户不知道卡在哪里，也不知道可操作什么 | 分离连接、消息交付、生成和音频状态 |
| P1 | 存档界面进度主要为 0→100；真实阶段在管理器里，未持续送到前端 | 长操作像卡死 | 真实任务阶段、失败原因及完成确认 |
| P1 | 时间加速藏在存档里；滑块每次变化都请求后端 | 功能难找、语义混乱；请求密集且失败后显示可能不一致 | 时间设置独立，释放后提交，显示已确认值 |
| P1 | 模型有五种表情，但没有 HitAreas、Motions 配置；服务没有发出匹配的表情提示 | “有角色”尚未成为连贯的角色表演 | 表现控制器＋模型资产契约与降级 |
| P1 | 远程与面对面共享同一套角色触摸行为 | 呈现与场景事实脱节 | 依据服务端交流方式决定可用操作 |
| P2 | 回忆主要停留在后端检索，近期轨迹为字符串展示 | 长期经历缺少可感知的结果 | 回忆册、约定、活动收尾和可追溯的记忆入口 |

## 3. 成功标准与体验原则

1. **回应可见**：用户不必先打开历史才能看到本轮回复。
2. **操作可解释**：发送、静音、暂停播放、打断生成、读档分别具有准确语义。
3. **阅读可控制**：阅读旧消息不会被新内容拉走，字幕不会自行消失。
4. **空间一致**：背景、角色、交流方式和可用动作遵守同一份服务端场景状态。
5. **等待可理解**：立即确认操作；模型慢时报告真实阶段，而不是伪造百分比。
6. **角色有连续性**：动作、表情、声音和文字属于同一个角色事件，不各自乱播。
7. **用户有自主权**：允许沉默、拒绝邀请、离开、静音和停止互动；不以惩罚离线制造粘性。
8. **失败可恢复**：保留草稿和已接受的操作，重试不重复执行；进程异常可回到一致状态。

## 4. 核心循环与信息架构

### 三个时间尺度

- **几秒钟**：输入或动作 → 即时反馈 → 角色看向用户/开始思考 → 回复或明确拒绝 → 文字、声音、表情收尾。
- **数分钟**：选择交谈/一起学习等活动 → 角色持续陪伴 → 自然结束或中断 → 一段有来源的回顾。
- **跨日**：重新进入 → 看到当前可确认的情境和上次未完成事项 → 选择继续或换话题 → 形成新的经历。

每个循环都应提供“可完成的体验”，而不只是持续消费聊天消息。首个活动建议做“一起自习”：有开始、计时、暂停、可选结束回顾，不制造好感度奖励。

### 主导航

- **陪伴**：角色舞台、当前对白、输入与当下可用动作。
- **回忆**：对话历史、重要回忆、已确认约定；默认以时间和事件组织。
- **存档**：继续、手动保存、快速保存、自动备份和加载预览。
- **设置**：声音、文字、显示、互动偏好、时间与后台运行、无障碍。
- **开发者面板**：PAD、完整角色独白、原始事件、模型/工具状态；独立入口，不混入默认主屏。

### 必须分开的三类状态

| 类别 | 值示例 | 谁能改变 | 对界面的影响 |
|---|---|---|---|
| 展示视图 | 舞台优先、对话优先、专注陪伴 | 用户选择，可记住偏好 | 只改变布局和信息密度 |
| 世界事实 | 双方位置、面对面/远程/未知、日程与时刻 | 服务端验证后提交 | 决定背景、交流方式和可用动作 |
| 系统状态 | 连接中、准备场景、生成中、语音失败、读档中 | 协议事件与客户端播放器 | 决定反馈及操作是否可用 |

切换视图不能传送角色、建立联系方式或开始活动。用户需要更正交流方式时，使用独立的“确认场景”操作，经服务端验证后再显示为事实。

## 5. 布局与视觉方案

### 舞台优先：推荐默认视图

- 顶部保留紧凑的角色名、场景位置、世界时间、交流方式和菜单。
- 中部以角色和环境为主；角色的脸、手及字幕使用明确安全区，避免被浮层盖住。
- 底部是稳定的当前对白与输入区，历史通过侧抽屉展开；默认显示本轮和少量最近上下文。
- PAD 雷达图、完整独白及长篇目标默认收起。状态以“正在看书”“有些困倦”等简短描述呈现，同时保留不确定性。
- 与场景无关的固定海景替换为匹配地点与时段的背景；缺少素材时使用统一中性背景并显示位置，不伪造已到达某地。

### 对话优先：长聊与手机使用

- 对话成为主要阅读区域，角色缩为侧边或顶部的小舞台。
- 远程场景采用消息交流表达；“正在输入/暂时离开”等文案必须有真实状态支持。
- 角色区可以折叠，但当前回复、声音控制和连接状态保持可用。
- 不强制逐句点击推进；持续自由输入仍是主操作。逐字显示和按句阅读只是可选显示设置。

### 专注陪伴

- 小型角色舞台、明确的学习活动状态、真实时间计时和最少的对话干扰。
- 主动发言策略改为用户可选的少打扰模式，不由前端随机生成关怀台词。
- 计时器使用真实单调时间，与世界的加速倍率无关。切换布局不自动开始或结束学习。
- 完成后可选择记录活动；不要求必须写总结或连续打卡。

### 视觉系统

- 建议温暖、克制的校园陪伴风格，使用稳定的实色或高不透明度阅读表面；环境图承担氛围，文字区负责可读性。
- 统一间距、圆角、阴影、字体、按钮和状态语义；不同模式共享同一套组件。
- 建议正文 16–18 CSS px、可调到 24 px；字幕另设字号、宽度与背景设置。数值为本项目设计起点，不是通用可访问性合格证明。
- 常规反馈约 100–180ms，抽屉约 180–240ms；尊重减少动态效果设置，避免永久晃动和大量玻璃模糊。
- 单一层级表：场景 → 角色 → 舞台字幕 → 应用控件 → 抽屉 → 模态弹窗 → 全局提示。由统一 Portal 承载弹层，避免依靠继续增大 z-index 修补。

## 6. 聊天与输入完整工作流

### 输入

- 改为 1–5 行自适应 textarea；组合输入期间 Enter 不发送。默认 Enter 发送、Shift+Enter 换行，可切换为 Ctrl/Cmd+Enter 发送。
- 草稿本地保存，按角色/会话隔离。网络断开时仍能编辑；不会静默自动发送旧草稿。
- 空输入不请求后端、不停止正在播放的声音。粘贴、长文本、选字和键盘焦点均有明确行为。
- 发送后立即出现待确认消息，服务端确认后改为已接收；落库确认再显示已保存。失败提供原内容重试，沿用幂等请求标识。
- 初次进入无记录时，用一个可直接输入的邀请和少量可编辑的开场建议；不显示已实现不了的麦克风按钮。

### 忙碌与打断

- 生成期间继续允许编辑草稿，默认不无限排队。一个活动轮次＋一个待发送草稿。
- 正在生成时提供“停止生成”；有新草稿时提供明确的“打断并发送”。停止声音单独控制，不伪装成已停止模型。
- 若服务端正处于无法即时取消的阶段，立即显示“正在停止”，并禁止晚到内容进入当前轮次；后端仍需实际结束旧任务，不能只在 UI 隐藏。
- 已经显示或听到的片段保留为“已中断”；未完成回复不写成完整的角色承诺。
- 打断不回滚用户已经确认的地点或联系方式；修改已完成剧情需要显式的分支或读档操作。

### 反馈与历史

- 分别显示连接、消息交付、场景准备、回复生成和声音状态；不用统一的“正在思考”掩盖全部阶段。
- 目标：操作反馈在本地 100ms 内出现。等待超过约 3 秒显示真实阶段，超过约 10 秒给出可用的停止/重试入口；这些是交互目标，不承诺模型延迟。
- 用户距离底部约 80px 以内才跟随新消息；离开底部后保持阅读锚点，显示“有新消息/回到最新”。
- 向上分页按第一条可见消息及其像素偏移恢复位置，不使用多个定时器强制滚动。
- 提供复制、重播、定位日期、搜索和收藏；收藏由用户明确操作，不意味着改写角色记忆。
- 历史、原始独白与系统日志分开。流式标签、工具 JSON 和异常堆栈不能进入玩家对白。

## 7. 声音、字幕与角色表演

### 单一播放控制器

- 统一管理音频生命周期、音量、自动播放、暂停、重播和失败；组件不自行 new Audio 争夺播放。
- 每段音频绑定会话、分支、轮次、消息和分段序号。读档、打断或切换会话后，旧音频必须失效。
- 自动声音默认沿用迁移后的用户偏好；新用户先通过明确操作启用。关闭后停止当前声音并丢弃待播队列，手动重播仍可单独发起。
- 文本正常出现不必等待 TTS。声音延迟或失败不阻塞阅读；失败在对应消息提供重试。
- 浏览器阻止声音时显示“点击启用声音”，不把限制当成已播放。
- 第一版只做可靠的整句/整条播放；第二版再做按句合成、按序播放和音素级同步。
- 每台设备独立控制声音；同一浏览器多个标签页默认只允许一个播放所有者。手动重播响应定向返回请求客户端。

### 表现调度

- 建立表现控制器，协调注视、眨眼、呼吸、口型、表情和一次性动作。
- PAD 作为缓慢变化的情绪底色；本轮对白的表现提示决定短时表情。避免每个 token 改一次表情。
- 冲突优先级明确：口型跟随正在播放的音频；被用户停止后立即回落；一次性动作结束后恢复底色；减少动态设置覆盖装饰动作。
- 后端只发出白名单内的表现提示；客户端依据模型能力映射，缺少表情或动作时回到中性，不产生异常或伪造素材。
- 内心独白改为可选的“角色独白”，允许固定、滚动与回看，默认不自动弹出。完整工具轨迹保留在开发者面板。

## 8. 角色互动与场景资产

### 互动的四个层次

1. 悬停、注视和按钮反馈属于本地界面反馈，不调用模型、不写长期记忆。
2. 招呼、询问近况等语义动作通过后端正常轮次处理。
3. 接触、递送物品等世界动作必须验证同处一地、角色当前状态和动作是否被接受。
4. 地点变化、开始活动、完成约定属于持久世界事件，需要后端提交。

前端可以即时表现“操作已收到”，不能在角色尚未回应前先播放“高兴地接受接触”。远程或位置未知时不显示身体接触入口；拒绝也应有清楚、自然的结果，不能被循环点击绕过。

### 命中与素材

- 移除全局右键按矩形划区的交互方式；普通点击/触摸为主，并提供相同能力的按钮和键盘操作。
- 当前模型没有 HitAreas，因此先做显式的语义动作按钮；取得合适的模型命中数据后，再加入精确命中。不得假定已有可用头部/身体区域。
- 模型命中坐标通过实际视口和模型变换换算，透明 Canvas 区域与弹窗必须不触发角色动作。
- 目前只有 normal/happy/sad/angry/questioning 五种表情配置，未配置动作组。首批姿态设计须明确哪些使用现有参数、哪些需要重新制作和导出。
- 首批背景建议覆盖图书馆、宿舍、校园室外三个地点，提供日间/傍晚/夜间变体；作为目标素材清单，非强行给当前模型补出不存在的资源。
- 每个场景资源记录 ID、显示名、角色安全区、允许镜头、可用动作和默认环境声。背景选择依据结构化场景，不通过扫描长篇情境文字随意切换。

## 9. 回忆、约定与轻度游戏化

- 回忆册把重要经历组织成事件卡：时间、参与者、地点、简短摘要和可回到的原始对话。
- 用户收藏、角色形成的记忆、系统推演分开展示。收藏不自动提升好感，推演不伪装成已经发生的回忆。
- 对记忆提供“这条不准确”的纠正入口；先定位来源，再发起更正，不能直接把 UI 修改当作角色已经知道。
- 约定展示时间、地点、确认状态以及来源。不从“改天一起去”自动生成确定日期。
- 优先开发一个完整活动：一起自习。之后再验证散步、阅读、讨论代码等活动；每种活动都要有可用条件、进行状态、中断和结束结果。
- 关系变化优先通过措辞、熟悉的话题和记得的细节表现。若以后加入关系数值，必须解释来源，避免变成可刷取的单一好感条。
- 离开后回来可选择简短回顾；不把未验证的离线模拟全部当作事实，不进行情感惩罚式催促。

## 10. 存档、时间与长操作

- 存档独立为页面或完整抽屉，展示角色/地点、世界时间、简短事件摘要、保存类型和预览；文件大小进入详情。
- 快速保存的完成提示只在真实成功后出现。自动备份、快速保存和手动存档分组，防止误删回退点。
- 加载前显示即将恢复的内容、当前进度处理方式和自动备份结果；不只显示浏览器原生 confirm。
- 存读档创建任务 ID，并持续报告等待当前对话、备份、恢复数据、重建场景和完成等真实阶段。未知耗时显示阶段与活动指示，不造进度。
- 真正不可中断的导入阶段不能提供假取消；可安全取消的准备阶段才显示取消按钮。
- 读档成功后依次刷新分支、状态、历史、表现和播放控制器，不整页 reload。重建失败保留恢复入口与任务信息。
- 第一版继续使用现有完整快照，添加分支/会话纪元防止旧事件混入；“从某条消息分支”需有对应的完整检查点，不能只截断前端消息。
- 时间倍率移动到“时间与后台运行”，预览与已提交值区分，释放滑块后提交；失败恢复实际值。世界时间与电脑时间明确标注。
- 暂停播放、关闭声音、勿扰与暂停世界分别定义。世界暂停若开放，需要后端同时冻结逻辑时钟和自主演化；不能只停 UI 计时。

## 11. 自适应、无障碍与设备体验

- 桌面宽屏可并列舞台和对话；中等屏幕只保留一个辅助抽屉；手机上下组织，取消细窄的三栏。
- 使用容器尺寸、动态视口高度和安全区；软键盘打开时保住输入与最近回复，避免固定 100vh 截断。
- 首轮测试覆盖 360×800、390×844、768×1024、1366×768 和 1920×1080，并测试 200% 文本缩放。
- 正文和字幕在实际背景合成后达到至少 4.5:1 对比度；大字适用的例外按 WCAG 判断。重要信息不用颜色单独编码。
- 本项目把主要触控目标设为至少 44×44 CSS px；这是高于 WCAG 2.2 AA 最小目标尺寸的项目目标，不混称为 AA 的统一强制值。
- 所有重要动作有键盘入口；快捷键可查看、可修改，不占用输入法组合操作，触屏不依赖右键或 hover。
- 模态弹窗具备正确名称、焦点约束、Esc 关闭及焦点返回；破坏性操作默认聚焦安全选项。
- 状态提示使用适度 aria-live，不逐 token 朗读；完成文本按消息提供可读语义。
- 声音、字幕、字体、减少动态、角色注视和触摸入口可独立设置。模型加载失败时仍能完整文字聊天，WebGL 上下文丢失提供恢复或静态头像。

这些设计依据 W3C WCAG 2.2 与 ARIA 模态对话模式，并借鉴 Xbox Accessibility Guidelines 的字幕、输入和焦点原则；本计划不等于已经通过可访问性审计。

## 12. 前端架构与后端接口

### 推荐架构

- 保留 React + Vite，新增模块逐步使用 TypeScript；不在第一阶段同时更换全部构建与图形依赖。
- 拆成应用布局、对话、角色舞台、播放器、场景、回忆、存档和设置等功能域。App 只负责组合与路由。
- 建立统一运行状态层，可用类型化 reducer/store；界面偏好、服务端事实和瞬时播放状态分别保存。
- WebSocket 在独立服务中连接、恢复和分发；UI 不直接解释原始 XML 风格标签。解析在一个适配边界完成，展示组件只接收对白或独白事件。
- 渲染器使用独立生命周期，不因每个 token 更新而重建 Canvas；尺寸来自容器。播放器、渲染器与业务状态之间通过清晰接口通信。
- 模拟服务能复现慢响应、断线、重复消息、乱序音频、静默回复、失败存档和加载失败，开发 UI 不依赖真实模型调用。

### 状态模型

不要用一个 isThinking 表示全部流程。最少分成：

- 连接：connecting / online / reconnecting / offline。
- 用户消息：submitting / received / persisted / failed。
- 轮次：queued / preparing_scene / generating / completed / interrupted / failed。
- 声音：idle / loading / ready / playing / paused / ended / failed。
- 世界任务：running / preparing_archive / restoring / recovery_required。

声音可以在文本完成之后继续加载，因此不能将以上状态全部串成单一线性枚举。

### 最小协议补齐

| 能力 | 接口要求 | 客户端行为 |
|---|---|---|
| 发送确认 | client_request_id、服务端消息 ID、接收与持久化确认 | 乐观展示，幂等重试 |
| 轮次关联 | turn_id、message_id；文本和声音有分段序号 | 绑定同一条回复，拒绝过期音频 |
| 恢复与读档 | session/branch_epoch、事件序号及状态版本 | 旧事件失效；断线后恢复快照与尾部事件 |
| 阶段反馈 | 场景准备、生成开始/结束/取消/失败 | 显示真实阶段，保留草稿 |
| 取消 | cancel_turn，服务端确认及终态；生成循环有取消检查点 | 只有确认后才结束旧轮次 |
| 语音 | 音频所属轮次、消息、段号和播放请求；手动请求的 client_id | 正确重播和本地播放策略 |
| 场景与表现 | 场景版本、位置、交流方式及可用动作；白名单表现提示 | 依据权威状态更新舞台 |
| 存档任务 | task_id、阶段、可取消性、结果与恢复状态 | 真实进度，无整页刷新 |
| 能力发现 | 是否有语音输入、哪些角色动作/表情、是否能取消 | 未实现能力不显示可用入口 |

优先在现有接口旁增加兼容事件与字段，保留旧客户端可用的过渡期。新客户端恢复时先取一致快照，再应用快照后的事件；仅靠时间戳去重不足以处理读档。

后端需要增补轮次/任务管理和取消检查点，但不在此轮重写 PAD、长期记忆检索或模型选型。分支纪元第一版用于隔离迟到事件，不能因此声称数据库已支持任意时间点重放。

## 13. 性能与质量目标

以下是待测量的验收目标，不是当前性能结论。

- 本地操作反馈目标 P95 <100ms；记录阶段耗时而非承诺 LLM 固定首字速度。
- 支持设备上，角色表现以流畅为目标；低性能档降到约 30 FPS，并可降低分辨率、关闭昂贵背景效果。先固定一台参考设备再定性能门槛。
- 角色渲染不触发整页 React 重绘；后台不可见时暂停装饰渲染，恢复后按最新状态重建。
- 模型、图表、存档与开发面板按需加载。先测量图形与文字布局开销，再决定是否升级 Pixi/替换封装。
- 连续 30 分钟测试无重叠声音、无重复角色实例、无持续增长的事件监听器和未释放音频对象。
- 1000 条合成历史的翻阅不丢锚点、不明显卡顿；是否引入虚拟列表由测量决定，并验证其可访问性与滚动恢复。
- 埋点默认本地记录操作与阶段耗时，不记录聊天正文。正式用户研究另行明确采集内容，不默认接入外部分析服务。

## 14. 交付阶段与优先级

工期仅用于排序：假设一名熟悉项目的前端开发者，后端可配合，基本美术可获得。完整 B 路线按约 6–10 周量级评估；复杂动作资产和语音输入另算，不作为承诺排期。

| 阶段 | 主要交付 | 进入下一阶段的门槛 |
|---|---|---|
| M0：体验基线与设计 | 核心任务走查、当前性能基线、三种布局线框、设计变量和交互状态表 | 发送/回看/静音/重播/读档等任务的行为达成一致 |
| M1：可靠交互底座 | 输入法、滚动、草稿、错误反馈、声音开关、统一层级、隐藏未实现按钮 | 现有功能可靠可用，先交付路线 A 的收益 |
| M2：统一状态与协议 | 发送确认、轮次标识、取消、音频绑定、模拟服务、兼容适配 | 重复/乱序/断线/取消场景都不会产生错误落库或错误播放 |
| M3：新应用框架 | 舞台/对话/专注视图，响应式布局、设置和辅助面板 | 同一会话无刷新切换；窄屏和键盘操作完整 |
| M4：角色与场景表现 | 三个地点的首批资源、表情调度、显式动作、能力降级 | 场景与世界事实一致；点击 UI 和透明区域不触发角色 |
| M5：回忆与活动 | 回忆入口、约定溯源、一次完整自习活动、活动回顾 | 活动有开始/结束/中断；没有伪造记忆或隐藏奖励规则 |
| M6：存档与发布验收 | 真实任务阶段、无刷新恢复、异常恢复、性能和无障碍测试 | 用户可独立完成关键任务，旧数据可读取，能回退 |

M2 是可靠打断和声音同步的前置条件；M4 取决于模型和场景资产；M5 不应抢在聊天可靠性之前。设计、素材清单与工程拆分可并行推进，但不以“全屏换皮已完成”替代行为验收。

### 第一批具体任务

1. 让最新回复常驻；历史阅读不再强制滚动到底部。
2. 修复中文输入、草稿与发送状态，移除未实现的麦克风入口。
3. 统一播放器，修正关闭声音的语义，先给音频补消息关联。
4. 统一层级与容器布局，移走默认 PAD/完整独白。
5. 接入真实阶段和取消协议，再开放“打断并发送”。
6. 以新布局承接上述模块，随后做角色表现与活动。

## 15. 验证计划与上线门槛

### 自动化

- 状态层与协议：正常、重复、乱序、丢事件、断线恢复、读档纪元切换及取消竞态。
- 输入：中文组合输入、长文本、粘贴、多行、连续发送、断线草稿保留与同请求重试。
- 声音：关闭后晚到音频、连续重播、自动与手动切换、TTS 失败、浏览器播放限制、两个标签页。
- 历史：正在阅读时新消息到来、向上分页、搜索定位、恢复滚动、纯独白与静默回复。
- 角色：界面遮挡、透明区、模型区域、缺少表情/动作、远程禁用接触、模型加载失败和 WebGL 恢复。
- 存档：操作等待、阶段反馈、失败保留当前状态、成功后历史/声音/舞台一致、恢复后旧事件不再生效。
- 工具建议：沿用现有测试，新增组件交互测试与浏览器端到端测试；全部使用合成对话和隔离数据。

### 用户研究

- 第一轮约 5–8 人，用于发现问题，不声称代表总体统计结论；包括重度聊天用户、视觉小说/陪伴类游戏用户及较少接触该类产品的人。
- 指定任务：首次发言、翻看旧对话、关闭声音后收到回复、重播指定一句、打断长回复、理解当前交流方式、保存与恢复、找回一个约定。
- 目标：关键任务无指导完成率至少 90%；无误触发送、无静音失效、无不可恢复的数据误操作。小样本不满足时，以具体失败原因迭代，不能仅以平均满意度放行。
- 记录发送到本地反馈、到服务器确认、到首段文字、到声音就绪及首次正确理解系统状态的时间；区分模型延迟与界面延迟。
- 对三种布局进行相同任务比较，再确定默认视图与信息密度。以理解、控制和沉浸感为主，留存和时长只作辅助指标。

### 发布与兼容

- 用功能开关或独立入口验证新前端，默认不同时让两套客户端争夺语音与角色控制。
- UI 偏好单独版本化；旧聊天、现有 .ember 存档和角色状态适配后继续可读。新增场景字段缺失时回退未知，不随意补事实。
- 先使用模拟服务和隔离库，再以明确范围做真实模型抽查。不得以测试为由清空业务库。
- 发布前保留可回退的前端版本与数据备份；协议升级需保留兼容适配，直到新客户端稳定。

## 16. 后续可扩展方向

在上述基础上，可进一步规划可探索校园、动态日程、阅读/音乐等共同活动、语音输入与低延迟语音、桌面小窗、移动端安装体验、角色编辑器、场景编辑器及多角色。

每个方向都需要独立验证：地图需要规则与内容制作，语音输入需要真实识别链路和权限反馈，桌面窗口需要平台集成，多角色需要会话与数据隔离。它们不是给现有按钮换个名字就能获得的能力。先做一个完整的小体验，再依据实际反馈扩大。
